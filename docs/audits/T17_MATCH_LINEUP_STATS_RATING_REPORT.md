# T17 比赛阵容、技术统计与球员评分审计报告

## 实现结论

T17 已形成可实际演示的闭环：5 张比赛数据表、4 个公开读接口、2 个登录写接口、比赛详情增强，以及完整的增量数据、校验、测试和 Windows 检查链路。评分写入使用事务、唯一键和原子 upsert；撤销采用 `CANCELLED` 与软删除，汇总不暴露用户身份。

## 开工审计与数据选择

- 开工时有 67 场 FINISHED 比赛，T16 阵容每队赛季范围仅 1-6 人，不能直接组成 11 人首发。
- 生成式 Demo 联赛中有 64 场比分、进球事件、事件球员与球队关系一致的安全比赛；按联赛、时间和 ID 稳定排序后选择 20 场，涉及 3 个联赛、9 支球队。
- 旧基础比赛 `50001`、`50004`、`50006` 的比分与 GOAL 事件不一致，明确排除，未修改比分或事件。
- 比赛的文本赛季为 `2026`，结构化赛季编码为 `2025-2026`；每个目标联赛仅有一个有效当前赛季，因此使用 `league_id + current_flag=1` 建立确定映射。

## 阵容扩充

`seed-t17-roster-expansion.sql` 使用 T17 专用 ID 段补充 108 名 Demo 球员。每支目标队的当前赛季阵容最终为 18 人：2 门将、6 后卫、6 中场、4 前锋。每名新增球员同时建立以下五层关系：

1. `football_player`
2. `team_player`
3. `football_team_season_player`
4. `football_player_team_history`
5. `football_player_competition_stat`

新增数据均带 `T17_DEMO_ROSTER`/`DEMO` 来源标记。专用 ID 段若存在非 DEMO 数据，脚本立即失败；不借用其他球队球员，不制造跨队转会历史。

## 比赛与评分数据

- 完整比赛：20 场；阵容头记录 40 条。
- 每场每队固定 11 名首发，阵型为 1-4-3-3，且有 1 名门将和 1 名队长。
- 当前数据库每场每队有 7 名替补，满足 5-7 人约束且包含替补门将；修正后的新库首次执行生成 5 名替补，重复执行不增长。
- 出场记录 720 条，实际出场球员统计 440 条，球队逐场统计 40 条。
- 15 名稳定 Demo 用户对 20 场最佳表现球员生成 300 条有效评分；评分值为 1.0-10.0、步长 0.5。
- `SUBSTITUTION` 事件只有单球员字段，因此按“该球员在事件分钟被换下”解释，不虚构换上球员；该规则已由校验覆盖。

比分等于球员进球合计，球队射门、射正、传球、牌和扑救等于球员统计合计。T15 只对 `source=DEMO` 的统计使用 `GREATEST` 向上补足：108 条新增球员赛事统计随阵容创建，另有 1 条既有球员统计因逐场总计需要调整；球队赛事统计无需调整。排名关键的比分、积分榜和旧事件均未修改。

## API、性能与安全

新增 lineups、stats、player-stats、ratings 四个 GET，以及评分 POST/DELETE。只允许 FINISHED 比赛中 `appeared_flag=1` 的球员被评分；同一用户重复评分覆盖原值，撤销幂等。最佳球员在单球员至少 3 个用户评分时采用用户均分，否则采用官方评分。

读取侧批量加载球队、球员和评分，循环中不调用关键 Mapper。结构查询上限保持为：lineups 5 条、team stats 2 条、player stats 6 条、ratings 5 条、rating submit 4 条，不存在随球员数量增长的 N+1。
